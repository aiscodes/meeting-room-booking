# Бронирование переговорной

Бронирование одной переговорной на рабочий день 09:00–18:00: выбор даты, просмотр, создание, редактирование и удаление броней.

Демо: _ссылка на Vercel_

## Запуск

Node.js 22+.

```bash
npm install
npm run dev
```

Приложение откроется на http://localhost:3000. Бэкенд не нужен, API замокан через MSW.

Проверки:

```bash
npm test
npm run typecheck
npm run lint
```

E2E-тесты (Playwright, сам поднимает dev-сервер на порту 3100):

```bash
npx playwright install chromium
npm run test:e2e
```

CI (GitHub Actions, `.github/workflows/ci.yml`) на каждый push и PR запускает lint, typecheck, unit-тесты, сборку и e2e на production-сборке.

## Стек

Next.js 16 (App Router), React 19, TypeScript, TanStack Query, React Hook Form, Tailwind CSS, Radix UI, MSW, Zod, Vitest, Testing Library, Playwright.

## Что сделано

Все бизнес-правила находятся в `src/domain/booking.ts`. Это чистые функции без React и сети. Их использует и форма (через resolver React Hook Form), и mock-сервер, поэтому клиент и сервер проверяют одно и то же.

| Правило | Реализация |
| --- | --- |
| 1. В пределах 09:00–18:00 | Бронь до 18:00 включительно допустима |
| 2. start < end | Ошибка на поле «Окончание» |
| 3–4. От 30 минут до 2 часов | Границы включительно |
| 5. Без пересечений | Интервалы полуоткрытые, 10:00–11:00 и 11:00–12:00 не конфликтуют |
| 6. Нельзя в прошлое | Прошедшие даты только для просмотра, прошедшие слоты сегодня недоступны |
| 7. Бронь не конфликтует сама с собой | При редактировании текущая бронь исключается из проверки |
| 8. 409 от сервера | Форма остаётся открытой с введёнными данными, показывается сообщение, список перезапрашивается, конфликтующая бронь подсвечивается |

Интерфейс:

- шкала дня с шагом 30 минут, клик по свободному слоту открывает форму с этим временем;
- в списках времени занятые и прошедшие варианты недоступны и подписаны;
- при смене начала окончание подстраивается;
- бронь можно перенести на другую дату: форма загружает расписание этого дня и, если выбранное время там занято, предлагает ближайшее свободное. После сохранения страница переходит на новую дату;
- идущие и завершённые брони нельзя изменить, они помечены. Если бронь началась, пока форма открыта, при сохранении появится сообщение об этом;
- дата хранится в URL (`?date=`), кнопки «Назад» и «Вперёд» в браузере переключают дни;
- расписание обновляется само раз в 30 секунд и при возврате на вкладку.

Состояния: загрузка, пустой день, ошибка загрузки с повтором, ошибка фонового обновления, отправка формы, подтверждение удаления.

Ошибки сервера: на 409 и 500 данные формы сохраняются, 400 раскладывается по полям, на 404 и 423 (бронь удалена или уже началась) диалог закрывается с сообщением.

Адаптив от 320 px. Доступность: подписи у полей, ошибки связаны через `aria-describedby`, серверные ошибки через `role="alert"`, фокус удерживается в диалогах, статус брони передаётся не только цветом.

## Структура

```
src/
  domain/      правила (booking.ts), тексты ошибок (messages.ts), работа со временем (time.ts)
  api/         клиент bookingsApi и типизированные ошибки
  features/    хуки запросов, логика формы, компоненты
  mocks/       mock-сервер на MSW и панель сценариев
  app/         страница и сборка экрана
```

Зависимости идут в одну сторону: `app → features → api → domain`. Фича не знает про моки, панель сценариев подключается только в `app`.

## Решения

Время хранится в минутах от полуночи, дата строкой `YYYY-MM-DD`. `new Date("2026-10-24")` парсится как UTC и западнее UTC даёт предыдущий день, поэтому даты так не парсятся. Текущее время передаётся в правила параметром, это упрощает тесты.

Сетевой слой отделён от UI: компоненты работают с `bookingsApi` и `ApiError`, `fetch` вызывается в одном месте. Ответы сервера проверяются Zod-схемами из `src/api/contract.ts`. Если формат не совпал с контрактом, UI получает понятную ошибку, а не падает на `undefined`. Тело ошибки тоже проверяется: при неожиданном формате тип ошибки определяется по HTTP-статусу. Для реального API достаточно задать `NEXT_PUBLIC_API_MOCKING=disabled` и `NEXT_PUBLIC_API_BASE_URL` (см. `.env.example`).

Mock API сделан на MSW, а не на Route Handlers. На Vercel serverless-функции не делят память, и in-memory хранилище теряло бы данные между запросами. MSW работает в браузере, запросы видны в DevTools, данные лежат в `localStorage`. Те же обработчики используются в тестах.

Оптимистичных обновлений нет: конфликты ожидаемы, поэтому показываю только подтверждённое сервером. После каждой записи, в том числе неудачной, список перезапрашивается. При переносе брони обновляются оба дня.

Обновление в реальном времени сделано опросом раз в 30 секунд, а не WebSocket: для mock API push-канал избыточен, а с реальным сервером опрос можно заменить на SSE или WebSocket без изменений в UI. Опрос не заменяет обработку 409: между обновлениями слот всё равно может занять кто-то другой.

Страница рендерится на клиенте, потому что расписание зависит от текущего времени пользователя.

## Как проверить 409

Кнопка «Mock API» в правом нижнем углу:

- «Другой пользователь занимает слот» добавляет бронь на сервере, интерфейс об этом не знает до следующего обновления (до 30 секунд). Если сразу выбрать это время и сохранить, придёт 409.
- «Конфликт при следующем сохранении» возвращает 409 на следующую запись, даже если данные свежие.
- Также можно включить ошибку 500, задержку ответа и сбросить данные.

## Допущения

- Шаг времени 30 минут.
- Идущие и прошедшие брони нельзя редактировать и удалять, сервер отвечает 423.
- Название необязательное, до 80 символов.
- Часовой пояс берётся из браузера. С реальным сервером нужен часовой пояс переговорной.

## Тесты

- `src/domain/booking.test.ts`: правила и граничные случаи.
- `src/api/bookings.test.ts`: сетевой слой (проверка контракта ответа, разбор 409, неожиданное тело ошибки, 204).
- `src/app/booking-app.test.tsx`: интеграционные тесты экрана с MSW (создание, 409, гонка, 500, редактирование и удаление, перенос на другую дату, кнопка «Назад», бронь началась при открытой форме, прошедшая дата, ошибка загрузки).
- `e2e/booking.spec.ts`: smoke-тесты в браузере на десктопе и мобильном вьюпорте (создание, редактирование, удаление, сохранение после перезагрузки, перенос на другую дату с возвратом кнопкой «Назад», 409 от сервера).

## Что не сделано

- выбор времени перетаскиванием по шкале: требует отдельной работы с мышью, тачем и клавиатурой, а ТЗ разрешает простой список;
- push-обновления через WebSocket или SSE вместо опроса;
- тёмная тема: дизайн по ТЗ не оценивается.
